# 环境与部署设计

现状：数据库Compose和迁移可按文档操作，尚无业务API/worker部署入口。本轮不启动或改动服务，不租云资源、不复用旧服务器配置。

开发/测试/生产分别独立数据库、凭据、卷和配置；开发与测试至少独立数据库服务实例，生产独立主机/网络权限。APP_ENV与库名匹配是误操作防护，不能替代网络和账号隔离。配置仅显式注入，样例敏感字段为空，不读旧.env。

目标部署：TLS入口→FastAPI进程；独立规划worker和推荐计算任务→同一新版本PostgreSQL。生产数据库不开放公网；运行角色仅DML，迁移角色DDL单独保管。生产禁止fixture/mock；外部依赖未配置时不能假装健康通过真实服务验收。

## 发布顺序

1. 检查源码/暂存区/历史和依赖，构建版本化制品，记录提交与迁移版本。
2. 对独立恢复副本演练迁移和备份恢复；确认旧客户端兼容窗口与回滚方案。
3. 用迁移角色升级，部署API/worker同版本，验证ready及任务领取。
4. 先小范围验证关键API与两端；错误升高时回退应用或兼容性前向修复，不对生产直接downgrade base。
5. 验证删除记录重放后再放行恢复环境；生产备份不得作为开发测试数据。

监控API错误/延时、数据库连接、任务队列年龄/超时/重试、第三方失败与限流；告警不包含用户聊天正文或凭据。备份频率、RPO/RTO及保留期为发布前待定项，不将示例当SLA。

详细初始化与恢复命令见[迁移与备份恢复](../03数据库/迁移与备份恢复.md)。前端通过各自构建产物交付，后端独立发布；当前没有容器化业务服务或自动生产部署完成的声明。
